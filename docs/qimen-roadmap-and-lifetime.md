# 奇门遁甲完善路线与终身局设计

本文是奇门遁甲后续开发的产品与技术设计基线，面向算法、结构化证据、提示词、API、MCP 和前端展示。内容以当前仓库的实际能力为起点；终身局目前是规划能力，不代表现有接口已经可以计算终身局。

## 快速结论

当前奇门已经能稳定生成一张有明确时间基准的单局盘，覆盖时家、日家、月家、年家，支持转盘/飞盘、拆补/置闰、九宫四盘、经典格局、复合格局、方位和相对节奏证据。当前入口是 <code>generateQimen(customDate, method, scope, juMethod)</code>，公开参数中的 <code>qimenScope</code> 仍只有 <code>hour</code>、<code>day</code>、<code>month</code>、<code>year</code>。

终身局不宜直接作为第五个普通排盘级别塞进现有 <code>QimenScope</code>。更稳妥的产品模型是：

1. 以出生时刻生成一张本命基础局；
2. 依据明确声明的门派或产品口径，把年命、日干、时干和宫位关系映射为人生主题；
3. 按明确的年龄边界生成阶段卡；
4. 只有用户指定范围时，才扫描年、月、日、时的动态触发；
5. 每条判断都回指基础盘、阶段盘或触发盘的证据链。

这样可以同时保留“终身结构”和“周期触发”，避免把静态本命盘写成必然事件表。

已有回归测试覆盖交节、晚子时、置闰、18 局六十时辰、九宫完整性、经典格局、宫间关系和证据提示词。后续工作应在这条基线上追加能力，不应让终身局绕开现有节气、干支和证据模块。

### 当前明确缺口

| 缺口 | 影响 | 处理方向 |
| --- | --- | --- |
| 没有终身局输入和结果类型 | 无法区分“出生基础局”和“当前占时局” | 新增独立终身局契约，不修改旧字段语义 |
| 没有出生资料标准化层 | 无法可靠处理时区、地点、真太阳时和出生时间准确度 | 先统一时间输入与误差策略，再生成基础局 |
| 没有阶段边界 | 不能把基础局组织成人生阶段，也无法重现阶段切换 | 将年龄算法、虚实岁和边界时刻写入结果 |
| 没有周期事件扫描 | 只能看到一张静态盘，无法体现阶段内动态触发和交互 | 增加按请求范围的动态盘扫描与事件聚类 |
| 没有终身证据图 | AI 容易把多个阶段的相似象意合并成无依据结论 | 让每个阶段、事件和主题结论保留事实来源与反证 |
| 没有终身局提示词 | 当前提示词只服务单张奇门盘 | 新增终身局专用任务结构，仍遵循可独立复制的完整任务书 |

## 总体路线

~~~mermaid
flowchart LR
    A[出生资料与时间标准] --> B[本命基础局]
    B --> C[个人标记与主题宫]
    C --> D[阶段边界与阶段卡]
    D --> E[指定范围的动态盘扫描]
    B --> F[基础证据]
    D --> G[阶段证据]
    E --> H[触发与事件证据]
    F --> I[证据汇总]
    G --> I
    H --> I
    I --> J[终身局结构化结果与提示词]
~~~

开发顺序采用“契约先行、计算可重现、证据随后、提示词最后、展示按需加载”。任何新结论都必须先能在结构化结果中找到事实来源，再进入网页、API 或提示词。

## 奇门完善路线

### P0：口径、输入与结果契约

目标是先把终身局与普通占时局分开，并把会改变结果的选择显式化。

- 保持现有 <code>QimenScope</code> 不变；普通奇门继续使用 <code>hour</code>、<code>day</code>、<code>month</code>、<code>year</code>。
- 新增独立的终身局输入与结果类型，例如 <code>QimenLifetimeInput</code>、<code>QimenLifetimeData</code>，不要用字符串绕过类型检查。
- 出生时间必须带时区或可解析的 IANA 时区；存在夏令时回拨歧义时要求调用方消歧。
- 第一版只接受精确出生时刻。若未来支持时间区间，应返回多套候选盘及差异，而不是静默选取一个时刻。
- 真太阳时作为显式选择，记录原始民用时间、修正后的时间、经度、修正秒数和跨日状态。
- <code>method</code>、<code>juMethod</code>、年龄算法、阶段长度和边界规则都写入结果；<code>schools</code> 只改变解读侧重点，不改变底层排盘。
- 性别、姓名和当前职业可以作为解读背景，但在没有明确依据时不参与起盘和阶段计算。

验收条件：同一输入在不同入口产生相同的基础局；缺少时区、时间无效、回拨未消歧和阶段规则不完整时明确报错；旧奇门接口的响应结构保持兼容。

### P1：终身基础局与阶段引擎

目标是生成可以复盘的“人生结构”，而不是先写一篇长报告。

1. 统一计算出生四柱，并记录历法、节气、晚子时和真太阳时口径。
2. 以出生时刻生成基础时家局，保留完整九宫四盘和现有证据分析。
3. 根据选定口径计算个人标记。年命、命干、日干、时干落宫及其主客关系分别记录来源，不把不同口径合并成一个无名的“命宫”。
4. 将人生主题映射到宫位。主题目录和映射规则必须可配置、可追溯；不能仅凭数组顺序或单个吉凶标签决定事业、婚姻、财务等结论。
5. 以阶段锚点生成阶段卡。阶段卡至少保留年龄区间、日历区间、使用的口径、主题宫、盘面变化和证据摘要。
6. 阶段长度、起始年龄和边界算法做成 <code>stagePolicy</code>。产品可以默认使用 15 年一阶段作为阅读组织方式，但必须同时显示实际起算规则；15 年不是所有奇门传承的唯一共识。

阶段引擎有两种可审计模式：

| 模式 | 作用 | 适用场景 |
| --- | --- | --- |
| 基础局映射 | 不重排每个阶段的九宫，只用出生基础局、个人标记和阶段边界解释人生结构 | 终身局默认模式，体积小、复现稳定 |
| 周期重排 | 在阶段锚点或用户指定日期重新生成日/月/时家盘，并与基础局建立关联 | 研究某阶段的触发、转折和事件窗口 |

两种模式不能混写成一张“看起来连续”的盘。结果必须标明每条事实来自基础局、阶段映射还是周期重排。

### P2：规则目录、动态触发与事件聚类

目标是把已有单局规则扩展成时间轴上的可解释变化。

- 建立规则登记表：规则名称、盘面条件、适用范围、来源、当前实现状态、测试样本和解释边界。
- 已有的天盘干与地盘干 81 组合继续作为基础目录；门、星、神、宫、干的交互分别登记覆盖率，不把尚未审计的组合写成“全量支持”。
- 为每个周期保存结构化变化：换节气、三元或局数变化、值符值使落宫变化、主题宫变化、门星神干关系变化、空亡填实、马星触发、伏吟/反吟和特殊条件。
- 将相邻周期中的多条触发合并为事件簇，事件簇包含起止范围、触发事实、支持事实、反证事实、涉及主题和建议核验的问题。
- 事件窗口优先使用相对节奏和触发条件。只有用户给出明确目标范围，才在该范围内返回候选日期或时段。
- 对同一时间同时出现的吉格、风险格、空亡和反证，保留并列关系，不用总分覆盖矛盾信息。

建议的触发优先级为：实际节气/定局边界 → 阶段边界 → 主题宫落点变化 → 值符值使与门星神变化 → 空亡/马星/伏吟反吟 → 具体格局与宫间关系。优先级用于组织阅读，不代表现实概率。

### P3：证据、提示词、API 与 MCP

目标是让终身局在机器调用和在线 AI 解读中保持同一套事实。

- 终身局证据至少分为计算事实、个人标记事实、阶段事实、周期变化事实、事件簇事实、反证事实和解释限制。
- 每个结论保存 <code>ownerFactKeys</code> 或等价来源键；没有来源的文字不能进入默认提示词。
- API 建议增加独立路径，例如 <code>/divination/qimen/lifetime</code> 和 <code>/divination/qimen/lifetime/prompt</code>；稳定前不要让旧 <code>/divination/qimen</code> 接受 <code>qimenScope: "lifetime"</code>。
- MCP 建议增加独立工具，例如 <code>divine_qimen_lifetime</code> 和 <code>qimen_lifetime_prompt</code>，描述中明确需要出生时刻和阶段范围。
- 终身局提示词使用完整任务书结构，正文只放当前任务、出生与排盘资料、阶段资料、动态触发资料、传统依据和输出要求。
- 终身局提示词要求 AI 按“传统断语 → 具象象意 → 现代场景 → 可核验行动”展开，并把基础结构、阶段趋势和事件窗口分开。
- 未选择具体主题时，先列出盘面候选，再依据问题选择用神；未给期限时输出相对节奏和触发条件。
- 提示词不应暴露仓库名、接口名、MCP 名、内部事实键、排序分数或生成过程。

### P4：前端、性能与研究闭环

目标是让完整结果可读、可加载、可复盘。

- 默认展示“人生总览 + 阶段时间轴 + 触发事件”；九宫细节和单条证据按阶段展开。
- 年、月、日、时扫描采用按需加载和缓存，默认不生成无限期全量时间轴。
- 阶段卡支持复制、导出和固定链接；导出内容必须保留输入口径和证据来源。
- 在内部审查样本中记录用户问题、选定主题、阶段范围和实际验证结果，区分“盘面命中”与“现实事件已验证”。
- 将结构化结果、提示词和网页摘要都从同一份终身局数据生成，避免三套口径逐渐漂移。

## 终身局设计

### 术语和产品定位

终身局是一个复合结果，不是一张可以脱离时间的“永久奇门盘”。本设计把它拆成三层：

| 层 | 内容 | 稳定性 |
| --- | --- | --- |
| 本命基础局 | 出生时刻对应的时家奇门完整九宫盘 | 由出生资料和排盘口径决定，可重现 |
| 人生结构层 | 个人标记、主题宫、阶段边界和阶段主线 | 由明确的产品/门派规则决定 |
| 动态触发层 | 用户指定范围内的年、月、日、时盘变化与事件簇 | 依赖具体时间和扫描范围，按需生成 |

终身局适合回答“哪些人生主题更容易在什么阶段被触发”“某阶段有哪些支持与限制”“当前问题在长期结构中的位置”。它不适合输出一条脱离范围、无需盘面依据的必然事件结论。

### 输入契约

| 字段 | 必填 | 口径 |
| --- | --- | --- |
| <code>birthDateTime</code> | 是 | 带时区的出生时间；需要精确到可确定时辰 |
| <code>timeZoneId</code> 或固定偏移 | 是 | 优先 IANA 时区；历史夏令时必须保留解析结果 |
| <code>location</code> | 条件必填 | 使用真太阳时或需要地点证据时提供经纬度和地点名 |
| <code>calendarType</code> | 是 | 明确公历/农历及闰月信息，不允许猜测 |
| <code>timeStandard</code> | 是 | 民用时间或真太阳时；记录原始值和修正值 |
| <code>method</code> | 否 | 默认转盘法，也可选择飞盘法 |
| <code>juMethod</code> | 否 | 默认拆补法；选择置闰时记录实际定局节气和置闰状态 |
| <code>stagePolicy</code> | 否 | 阶段起点、长度、虚实岁、边界算法和输出范围 |
| <code>periodRange</code> | 否 | 要扫描的公历起止时间；未提供时只返回基础局和阶段结构 |
| <code>topics</code> | 否 | 事业、财务、关系、迁移、学习、健康风险等主题；只作为取证范围 |
| <code>gender</code>、<code>name</code> | 否 | 解读背景资料；除非明确选择的规则需要，否则不参与计算 |

### 计算层次

### 基础局

基础局必须复用现有奇门主入口和证据模块，至少包含：

- 出生四柱、实际排盘时间、时间标准和节气证据；
- 阴阳遁、局数、三元、定局方法、值符和值使；
- 一至九宫的天地人神四盘、天地盘干关系、经典格局和复合格局；
- 空亡、马星、特殊条件、方位和相对节奏；
- 九宫覆盖事实、规则来源和解释限制。

### 个人标记与主题宫

个人标记不能以“命宫”一个字段概括。建议至少分别保存：

- 年命地支及其落宫；
- 年干、日干、时干及各自落宫；
- 采用的遁干替代规则；
- 主题与候选宫的映射来源；
- 候选宫之间的支持、制约、同宫和对冲关系。

同一个主题可以有多个候选宫。选择结果由问题和取用规则决定，盘面候选本身不等于最终用神。

### 阶段卡

每张阶段卡应包含：

| 字段 | 说明 |
| --- | --- |
| <code>stageIndex</code> | 阶段顺序，从 0 开始或从 1 开始必须固定 |
| <code>ageStart</code>、<code>ageEnd</code> | 展示年龄和实际起止日期分别保存 |
| <code>calendarStart</code>、<code>calendarEnd</code> | 用完整日期时间表达边界 |
| <code>anchorRule</code> | 说明阶段起点采用生日、节气、虚岁或其他规则 |
| <code>basePalaceRefs</code> | 关联基础局主题宫或个人标记 |
| <code>periodChanges</code> | 阶段内已计算的局数、宫位、门星神干和特殊条件变化 |
| <code>eventClusters</code> | 阶段内按范围请求生成的事件簇 |
| <code>evidence</code> | 阶段事实、支持、反证和规则来源 |
| <code>limitations</code> | 该阶段可支持的解释边界 |

第一版默认只生成阶段主线，不自动展开所有年份。用户请求“某阶段细看”或提供 <code>periodRange</code> 后，再生成周期重排和事件簇。

### 动态触发和事件簇

动态扫描不是把每个日期的吉凶逐条罗列，而是寻找同一主题在一段时间内的结构变化。一个事件簇至少包含：

- 时间范围和边界原因；
- 触发盘的排盘范围、局数、值符值使和主题宫；
- 门、星、神、天盘干、地盘干以及宫间关系的变化；
- 空亡填实、马星发动、伏吟/反吟、节气切换等触发事实；
- 支持事实、反证事实和仍需核验的事实；
- 适合用户复盘的现实问题和行动窗口。

事件簇名称描述盘面主题，例如“关系主题出现重复触发”“迁移主题在节气切换处变动”，不直接使用“必然结婚”“必然破财”等结果化标题。

### 建议结果结构

下面是规划接口，不是当前已发布类型。字段名用于讨论数据契约，正式实现时应与现有结果协议一起确定版本。

  personalMarkers: QimenPersonalMarker[];
  topicCandidates: QimenTopicCandidate[];

  triggerFactKeys: string[];
  supportFactKeys: string[];
  counterFactKeys: string[];
  rhythm: '快' | '中' | '慢' | null;
  verificationQuestions: string[];
}
~~~

正式类型需要补充输入、证据和版本迁移定义；以上结构的重点是让“基础盘、阶段、动态事件、证据和提示词”各自有明确归属。

## 终身局提示词契约

### 资料顺序

终身局提示词按以下顺序组织资料，便于任何在线 AI 独立读取：

1. <code>【当前时间】</code>：本次解读生成时间及其时区。
2. <code>【问题】</code>：用户原问题和已选择的主题范围。
3. <code>【起盘依据】</code>：出生时间、历法、时间标准、排盘方法、定局方法和阶段规则。
4. <code>【终身局基础盘】</code>：四柱、局数、值符值使、九宫四盘和规则命中。
5. <code>【个人标记】</code>：年命、命干、日干、时干的落宫及其来源。
6. <code>【阶段资料】</code>：年龄区间、实际日期、阶段主题宫和阶段证据。
7. <code>【周期触发】</code>：用户指定范围内的周期变化、事件簇和相对节奏。
8. <code>【传统依据】</code>：实际命中的规则名称、传统依据和适用范围。
9. <code>【输出要求】</code>：分析顺序、证据引用方式、现实核验和行动建议格式。

### 解读输出要求

提示词应要求在线 AI：

- 先说明采用的终身局口径，再分开解释基础结构、阶段主线和动态触发；
- 每个结论紧跟盘面事实，引用对应的宫位、门星神干、格局、节气或周期事实；
- 依次完成“传统断语 → 具象象意 → 现代场景 → 可核验行动”；
- 对同一阶段的支持与反证并列说明，解释为什么形成拉扯或需要等待；
- 将盘面候选和问题取用分开呈现，说明缺少问题背景时只能保留候选；
- 将相对节奏、触发条件和用户给定期限分开，只有在资料支持时才细化时间窗口；
- 把现实核验问题写成用户可以回答的事实，例如合同状态、沟通频率、地点变化、身体检查或资源约束；
- 对健康、投资、法律和人身安全等主题给出核验与求助路径，不把传统象意写成现实保证。

产品侧应检查提示词实际生成的文字是否仍然是完整、可独立复制的任务书。提示词中只出现当前任务所需的排盘资料和传统依据，不把仓库、接口、工具、内部字段或实现状态传给在线 AI。

### 完成标准

终身局进入正式入口前，同时满足以下条件：

1. 输入、阶段和周期口径都有版本化契约；
2. 每个公开结论都能追溯到至少一条计算或规则事实；
3. 基础局与现有奇门单局结果一致；
4. 边界样本、跨时区样本和阶段切换样本通过回归；
5. API、MCP、网页摘要和提示词来自同一份结构化结果；
6. 默认输出不会把相对节奏转换成无依据的固定日期、成功率或吉凶总分；
7. 文档、OpenAPI、MCP README、核心 API 文档和 Skill 参数同步更新。

## 实施与兼容策略

推荐按以下提交顺序拆分，便于每一步独立审查：

1. 结果契约与输入归一化；
2. 基础局复用和个人标记；
3. 阶段引擎及边界测试；
4. 动态扫描、变化记录和事件聚类；
5. 终身证据汇总与提示词；
6. API、MCP、前端时间轴和导出；
7. 文档、示例、OpenAPI 和 Skill 同步。

兼容原则：

- 不修改现有 <code>generateQimen</code> 四个范围的含义；
- 不让终身局字段污染普通 <code>QimenData</code>；
- 旧调用方继续获得原有字段，新增字段使用可选或独立版本；
- 终身局输入不完整时返回可解释错误，不退回当前时间或普通时家盘；
- 终身局提示词只消费公开的结构化资料，不直接拼接内部审计对象。

## 开发前需要固定的口径

以下选择会直接影响结果，应在编码前写入版本化配置：

| 选择 | 推荐初始值 | 原因 |
| --- | --- | --- |
| 基础盘 | 出生时刻时家、转盘、拆补 | 与现有默认入口一致，便于复用和核验 |
| 时间标准 | 民用时间为基准，真太阳时显式开启 | 不把地点修正静默混入所有用户 |
| 阶段展示 | 15 年一阶段，实际起止日期单独保存 | 便于阅读，同时承认这是组织方式而非唯一古法 |
| 年龄模式 | 默认周岁，支持显式虚岁 | 避免年龄文字与日期边界混淆 |
| 动态扫描 | 无范围只看结构，有范围才扫描周期 | 控制输出体积，避免制造“全生涯逐日预测” |
| 默认主题 | 先展示候选宫，不自动选择单一用神 | 保留问题依赖和门派差异 |
| 性别影响 | 默认不参与计算 | 避免没有依据地改变奇门盘面 |
| 高风险主题 | 输出核验问题和现实求助路径 | 让传统资料服务于决策，而不是替代专业判断 |

这些口径确定后，才适合把终身局加入公开 API、MCP 和网页入口。当前阶段可以继续完善规则目录、证据字段和测试夹具，但不应提前对外宣称已经支持奇门终身局。
