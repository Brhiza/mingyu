# 维护复杂度系统排查计划

- 排查日期：2026-10-26。
- 基线：`6d0aaa10`（分支 `codex/classical-prompt-options`，开始时工作区干净）。
- 目标：找出让一次普通变更跨越过多模块、产生重复维护点、隐藏行为或增加验证成本的底层设计，形成可分批执行的简化路线。
- 本轮交付：系统地图、覆盖记录、证据化问题清单、必要复杂度说明、按依赖顺序排列的简化建议。本轮不修改运行时代码，不变更公开接口或部署配置。

## 1. 判断标准

不能仅凭文件大、代码多、存在接口/工厂/适配器就判为过度设计。每个正式问题必须回答：

1. 具体职责是什么，当前有哪些真实调用方和约束？
2. 哪些分支、层次或定义承担同一职责，修改时为什么必须同步理解或同步修改？
3. 是否存在更小且能够维持现有契约的实现？其复杂度是否只是转移到了别处？
4. 删除或收敛的边界是什么，哪些外部兼容性和行为需要保护？
5. 用什么检查证明维护成本下降、行为没有变？

重点识别：重复事实源、只有转发价值却暴露内部结构的层次、没有可证实扩展需求的通用机制、迁移结束后并存的新旧实现、过宽的公共边界、相互交叉的状态和回退、将输出裁剪放在昂贵计算之后、为了适配构建工具而侵入业务的结构。

需要单独保护：历法与时区边界、随机结果重放、真实算法差异、npm 已公开子路径、协议安全/输入限制、不同运行环境的必要适配，以及有独立真值来源的算法回归测试。

## 2. 分阶段方法与完成标准

| 阶段 | 方法 | 完成标准 |
| --- | --- | --- |
| A. 建立基线 | 读取维护约束、包与构建配置，按运行面和职责统计第一方逻辑，排除生成数据与供应商代码 | 明确源码边界、入口、依赖方向、测试层级与不确定项 |
| B. 风险定位 | 结合近期非 merge 历史、文件职责、依赖聚合与消费者数量定位热点 | 每个深入样本都有选取理由；历史 churn 只用于选样，不直接构成结论 |
| C. 分区审查 | 并行检查核心公共层、API/MCP、应用状态与编排；另查构建、发布和验证成本 | 每区记录审查文件、候选问题、反证与必要复杂度 |
| D. 纵向追踪 | 从真实入口追踪代表用例，检查参数、校验、计算、序列化、提示词与持久化的职责分布 | 验证问题是否真实进入运行链路，识别重复定义与变更放大 |
| E. 交叉复核 | 核查高影响结论的源码、调用方、测试/文档契约；执行针对性的只读检查 | 正式问题有精确路径/行号、影响解释和最小简化方向；推测单独列出 |
| F. 路线设计 | 按收益、变更风险与前置依赖排序，给每批设置可检查的退出条件 | 输出可执行批次，避免一次性重写和新增一套“统一框架” |

## 3. 分区职责与抽样

### 核心公共层

范围：`packages/core/src` 的公共入口、client/profile/birth/compatibility/synthesis、capabilities/foundation/shared、prompt 与领域适配边界。

重点：高层入口是否真正被消费；同一份输入/结果是否多次规范化；错误体系、序列化和能力清单是否形成平行协议；公共 exports 是否承诺了过多内部结构。算法内部只选热点，数据表与经典文本不作为逻辑膨胀证据。

### HTTP / REST / MCP

范围：`src/lib/public-api`、`mcp/src`、`src/lib/mcp`、`functions`、`server`。

重点：接口目录、schema、处理器和文档是否有重复事实源；Node 与 edge 是否只是薄适配；预设、范围限制、输出模式与分页是否互相叠加；异常、资源保护与回退是否多层改写。

### 应用编排与状态

范围：`src/pages`、`src/components`、`src/lib` 中应用专属逻辑、`src/workers`、持久化与 AI 客户端。

重点：同一业务是否有平行计算入口；派生状态是否重复保存；Worker、取消/重试、缓存与降级是否形成隐藏状态机；表单与结果恢复是否依赖彼此的内部结构。

### 构建、发布与验证

范围：Vite/TypeScript/workspace 配置、`build`、`scripts`、CI、核心和 MCP 发布链路、测试组织。

重点：双构建与源码/产物混用；手工维护的外部依赖知识；构建后补丁与重复生成；检查是否验证真实契约，还是依赖源码形状；现有测试成本是否与业务风险匹配。

### 纵向代表用例

优先追踪：出生资料进入八字/紫微及合参；奇门/星盘的范围选项；随机占卜的结果重放；提示词选项跨网页、REST 和 MCP 的传播。样本依据结构图与历史热点调整，并在报告里记录实际覆盖，不宣称逐行审查所有算法。

## 4. 证据格式与优先级

每项记录：问题、具体维护负担、至少一条实现证据与一条消费者/测试/历史证据、必要约束、最小简化方向、风险、验证条件、可信度。

- P1：日常跨入口变更会频繁经过，存在规则漂移或系统性耦合，适合优先规划收敛。
- P2：局部维护成本明确，但需依赖前一批整理或兼容迁移。
- P3：低频清理或仍需补充使用证据，不能据此直接删除公开能力。
- 已证实：源码路径和实际消费者/契约均已核对。
- 待验证：只能提出假设，需运行证据、外部使用信息或产品决定；不混入已证实问题计数。

## 5. 验证与报告边界

第一阶段使用静态依赖、调用方检索、源码与测试对照、git 历史和必要的零依赖定向测试。用户要求“继续深入，该安装构建的就操作”后，第二阶段按锁安装，补齐全量回归/穷举、各运行面构建、真实协议/选定页面验证及本机测量。安装、构建和生成产物在该授权内；诊断仍不改业务源码或公开契约，也不调用线上付费服务。第二阶段完成结果见 [运行验证记录](2026-10-26-runtime-validation.md)。

静态“无仓库内调用方”不代表 npm 外部无人使用；兼容层是否可删除必须先确认版本承诺。保留 Node/Cloudflare/Android 是产品支持范围，本轮只评价维持它们的实现成本，不代替维护者决定下线。

报告必须同时写出：实际覆盖、未覆盖、已证实问题、应保留的复杂度、可先执行的批次及其验证条件。基线不会因本轮新增审计文档而改变。
